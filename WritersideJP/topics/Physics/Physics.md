# 物理

<tldr>
<p>
Vite の物理スタックは <b>PhysX 3.4</b> を使用し、固定タイムステップのシミュレーション、最新のツールチェーン、NVIDIA Blast、大量のインスタンス化剛体のための Vite 独自の拡張を備えています。このページではまず測定結果を示し、次にその背景にある CPU アーキテクチャを説明します。バックエンドの機能は <a href="PhysX.md">PhysX</a> のページで扱います。
</p>
</tldr>

<img src="ChaosVsPhysX3000.png" alt="3,000 個のキューブのシミュレーションのエンジン内比較。Unreal 5.7 の Chaos は 33.26 FPS、Unreal Vite 26 の PhysX 3.4 は 157.88 FPS" border-effect="line"/>

*エンジンが管理する 3,000 個のキューブ。シーンもプリミティブ数も同一です。Chaos を使う Unreal Engine 5.7（左）は
33.26 FPS、PhysX 3.4 を使う Unreal Vite 26（右）は 157.88 FPS で動作します。*

Vite は物理をフレームタイムに直結するエンジンシステムとして扱います。シミュレーションのコストはソルバーだけではありません。ブロードフェーズ、接触の生成、アイランドの構築、コンストレイントの準備、反復的な求解、積分、コールバック、そしてエンジンの状態との同期のすべてが、最終的な物理時間に寄与します。

## エンジン内のキューブのワークロード

[Vite PhysX Cube Test](https://github.com/ViteStudio-Tech/Vite-PhysX-Cube-Test) は Unreal Engine の中で動作するため、その数値には出荷されるゲームが支払う周辺のエンジン処理も含まれます。公開されている
[キューブ生成の実装](https://github.com/ViteStudio-Tech/Vite-PhysX-Cube-Test/blob/5ae89c3b7b9d6993fdc535a54769e39ca7a116b4/Source/PhysXTest/CubeSpawner.cpp)
は、キューブごとに `UStaticMeshComponent` を 1 つ作成してエンジンに登録し、`SetSimulatePhysics(true)` でシミュレーションを有効にします。スポナー自体は 1 つの `AActor` なので、これは 3,000 個の Unreal アクターを個別に生成するのではなく、エンジンが管理するコンポーネントのパスを測定しています。

### エンジンが管理する 3,000 個のキューブ {id="cubes-3000"}

このページの冒頭に示した同条件のキャプチャでは、どちらのエンジンでも 3,000 個のキューブを生成し、3,016 個のプリミティブを描画しています。後述の Box Container Pile 10K のランナーとは異なり、これらの値には周辺の Unreal のランタイム処理が含まれており、物理ソルバー単体のミリ秒ではありません。

| 報告された指標 | Unreal 5.7 — Chaos | Unreal Vite 26 — PhysX 3.4 | Vite の相対結果 |
|---|---:|---:|---:|
| 生成したキューブ | 3,000 | 3,000 | 同一 |
| 描画したプリミティブ | 3,016 | 3,016 | 同一 |
| FPS | 33.26 | 157.88 | **4.75 倍** |
| フレームタイム | 30.07 ms | 6.33 ms | **78.9% 減** |
| ゲーム時間 | 30.01 ms | 6.11 ms | **79.6% 減** |

キャプチャした Chaos のゲーム時間は Vite PhysX の **4.91 倍**、フレームタイムは **4.75 倍** です。どちらのキャプチャでもゲーム時間がフレームのほぼ全体を占めているため、この結果は GPU 律速の比較ではなく CPU 側の比較です。

</warning>

Chaos は他の SDK のようなヘッドレスではなく、Win64 経由で計測する必要がありました。

Vite PhysX は 1 スレッドの 35.60 ms から 6 スレッドの 11.76 ms まで短縮され、**スループットは 3.03 倍** になります。NVIDIA PhysX 3.4 は 49.61 ms から 15.82 ms で **3.14 倍**、Chaos は同じ範囲で 1,052.09 ms から 791.97 ms で

同じスレッド数で比べると、Chaos は **1 スレッドで標準の NVIDIA PhysX の 21.21 倍**、**6 スレッドで 50.06 倍** の時間がかかります。NVIDIA PhysX は共通のスレッド数全体で Vite PhysX の 1.34〜1.39 倍の時間がかかり、言い換えると Vite は
NVIDIA PhysX 3.4 の基準に対して物理時間の中央値を **25.2〜28.2%** 削減しています。60 Hz の予算である 16.67 ms に、Vite PhysX は 3 スレッドで、NVIDIA PhysX は 6 スレッドで収まります。報告された Chaos の結果は 24 スレッドでも予算に収まりません。

1 スレッドの結果は、タスクのスケーリングだけでは差のすべてを説明できないことを示しています。ワーカーによるスケーリングの前の時点で、報告された物理時間は Chaos が Vite PhysX の 29.55 倍、NVIDIA PhysX の 21.21 倍です。マルチスレッドの結果は、ソルバーの処理、データアクセス、コリジョンとコンストレイントの処理、ビルド構成、エンジン統合を含む差を、スケーリングがさらに広げることを示しています。標準の NVIDIA の結果は、PhysX の基本アーキテクチャと、Vite の PhysX ビルドによる追加の改善とを切り分ける役割も果たしています。

## 差が生じる理由: 物理の CPU アーキテクチャ

### スレッド化とクリティカルパス

PhysX と Chaos はどちらもマルチスレッドのシミュレーションに対応しています。Chaos は Task Graph を通じて実行し、専用の物理スレッドを使い、パーティクル、コリジョン、アイランドの一部の処理を並列化できます。専用スレッドは処理をゲームスレッドから移しますが、それだけではシミュレーションの 1 ステップの開始から終了までの時間は短くなりません。

物理には順序付きのフェーズとデータの依存関係があります。連結したアイランド内のコンストレイントをすべて独立に解くことはできず、後の段階は前の段階が生成する状態を待たなければなりません。したがってスケーリングは、独立したアイランドの数と大きさ、タスクの粒度、同期の頻度、そしてゲーム側と物理側の表現の間で受け渡す状態の量に左右されます。

PhysX 3.4 は、依存関係で結ばれた `TaskManager` と `CpuDispatcher` を提供します。シミュレーションの各段階は
`LightCpuTask` のジョブを作成し、前提条件が満たされるとエンジンのワーカープールに投入します。Vite の Unreal 統合では、ディスパッチャーへの投入をまとめることで、スケジューリングのオーバーヘッドと利用可能な並列性を調整できます。NVIDIA の [PhysX 3.4 のスレッド化に関するドキュメント](https://docs.nvidia.com/gameworks/content/gameworkslibrary/physx/guide/Manual/Threading.html?highlight=cpudispatcher)
を参照してください。

### SIMD の適用範囲

Chaos には任意で使える Intel ISPC のカーネルがあります。ISPC は SIMD の技術で、対象 CPU のベクトルユニット向けに
SPMD プログラムをコンパイルします。重要な制約は「ISPC か SIMD か」ではなく、適用範囲と使用率です。ISPC のカーネルで実装された処理だけがそのベクトルパスの恩恵を受けます。分岐する接触、間接的なメモリアクセス、ギャザーとスキャッター、種類の異なるコンストレイント、ポインターの多いデータは、実効的なレーンの占有率を下げます。Intel の
[ISPC のドキュメント](https://ispc.github.io/index.html) に、コンパイラと SIMD の実行モデルの説明があります。

PhysX のナローフェーズとソルバーは、バッチ化された float データとプラットフォームの SIMD カーネルを中心に開発されています。有用な指標は、スカラーのまま残る処理やデータの移動で失われる時間も含めた、シミュレーションのステップ全体での実効的なベクトル占有率です。

PS5 の CPU では、その占有率は **256 ビットの FMA パイプ 1 本**（`FP3` は削除、`FP2` はストア専用）に当たります。デスクトップや Series X の Zen 2 のような 2 本の FMA パイプではありません。FMA のスループットに律速されるソルバーの処理は、同じクロックの 3700X のおよそ半分の速度で動作します。Vite の PhysX 3.4 の近代化を 4700S で計測しているのはそのためです。カーネルは FMA を融合した形（`V3ScaleAdd`）と SoA のまま保ってください。デスクトップの Ryzen や
Series X のキャプチャを PS5 の結果として扱わないでください。パターンは [PS5 CPU の FPU](PS5-CPU-FPU.md) にあります。

### 数値の精度

UE5 のラージワールド座標により、コアとなるワールド空間の型は倍精度に変わりました。Epic の
[LWC のドキュメント](https://dev.epicgames.com/documentation/unreal-engine/large-world-coordinates-in-unreal-engine-5)
は、Chaos の破壊で倍精度を使うことを明記しています。ただし、これはあらゆる Chaos のサブシステムのすべてのフィールドが
FP64 だという意味ではありません。最新の Chaos は一部のパスで混合精度を使い、UE4.27 のベースにある実験的な Chaos の実装は主要な `FReal` を `float` の別名にしています。

倍精度でも SIMD は使えます。ただし固定幅のレジスタに入る double の数は float の半分です。256 ビットのレジスタには
64 ビットの値が 4 つ、32 ビットの値なら 8 つ入ります。double ベースのフィールドは、同等の float のフィールドの 2 倍のストレージとメモリ帯域も必要とします。影響を受けるカーネルでは、理論上の要素スループットの低下、キャッシュの負荷の増加、float と double の境界での変換処理の追加が起こりえます。Epic の
[LWC 変換ガイド](https://dev.epicgames.com/documentation/unreal-engine/large-world-coordinates-project-conversion-guidelines-in-unreal-engine-5)
は `VectorRegister4f` と `VectorRegister4d` の両方を説明しています。制約はレーン幅とデータのコストであり、ベクトル命令がないことではありません。

FP64 のコストを表す普遍的な割合はありません。スカラーの FP32 と FP64 の命令は CPU によってはほぼ同じレイテンシーである一方、ベクトルのスループットや帯域に律速されるカーネルでははるかに大きな差が出ることがあります。割合を示す場合は、特定のワークロード、プラットフォーム、ビルドに紐付けなければなりません。

## 比較を再現する

エンジンの判断のために管理された比較を行うには、次のようにします。

1. エンジンとベンチマークプロジェクトの両方のコミットを固定します。
2. コンパイラの最適化、チェック、ログ、計測の設定をそろえます。
3. コリジョン形状、マテリアルの設定、ソルバーの反復回数、スリープ、タイムステップ、イベントの生成をそろえます。
4. スレッドのアフィニティと、ハイブリッド CPU での P コアと E コアへの配置を記録します。
5. 生のフレームサンプル、中央値、パーセンタイル、分散を公開します。
6. 適切な CPU プロファイラーで、ソルバーのクリティカルパスとワーカーの使用率をキャプチャします。
7. 代表的な製品のシーンでも繰り返します。10,005 個のボディがすべて起きている山積みは負荷試験用のワークロードです。

    </step>
    <step>
        PhysX は安定したフレームレートで最もよく動作します。非常に高い、または不安定なフレームレートではスタッターが起こることがあるため、フレームペーシングを安定させるよう FPS に上限を設けてください。
        <code>MaxDepenetrationVelocity</code> を 100 程度に設定することも、不安定なフレームペーシングによるスタッターを減らすのに役立ちます。
    </step>
</procedure>
