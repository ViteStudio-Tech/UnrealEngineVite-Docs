# PhysX

<tldr>
<p>
Vite は剛体シミュレーション、コリジョンクエリ、コンストレイント、ビークル、スケルタルの物理に
<b>NVIDIA PhysX 3.4</b> を統合しています。さらに、最新のコンパイラ対応、固定タイムステップのシミュレーション、NVIDIA Blast、大量のボディを扱うインスタンス化物理サブシステムでバックエンドを拡張しています。
</p>
</tldr>

<img src="PhysicsCubeBench.png" alt="1,400 個のキューブのシミュレーションの比較キャプチャ。Chaos は 75.45 FPS、PhysX 3.4 は 148.44 FPS" border-effect="line"/>

*同じシーンでシミュレーションする 1,400 個のキューブ。Chaos（左）はフレーム 13.25 ms で 75.45 FPS、Vite の
PhysX 3.4（右）はフレーム 6.74 ms で 148.44 FPS です。方法の詳細は
[物理キューブベンチマーク](Physics-Cube-Bench.md) を参照してください。*

PhysX は Unreal Engine の標準の物理フレームワークを通じて公開されています。ボディインスタンス、物理マテリアル、物理アセット、コリジョンプロファイル、コンストレイントコンポーネントといった既存のエンジンの型は、内部で PhysX のシーンを使います。そのため、UE4 のゲームプレイコード、ブループリント、コンテンツは、物理のための移植作業なしに動作します。

## 概要

<deflist>
<def title="エンジン内で Chaos より高速">
エンジンが管理する 3,000 個のキューブが、同じシーンの Chaos を使う Unreal Engine 5.7 の 4.75 倍のフレームレートで動作します。同条件のキャプチャは <a href="Physics.md">物理</a> を参照してください。
</def>
<def title="標準の PhysX より高速">

25.2〜28.2% 少なく、CPU 版の標準 PhysX 5.6.1 より 1.15〜1.44 倍高速です。いずれも 1〜6 のすべてのスレッド数で成り立ちます。
</def>
<def title="UE4 のコンテンツに必要な機能を網羅">
剛体、シーンクエリ、コンストレイント、ラグドール、ビークル、APEX Destruction、APEX Cloth、NVIDIA Blast。UE5 が削除・置き換えたシステムも引き続き利用できます。
</def>
<def title="製品開発のための設計">
固定タイムステップのシミュレーション、大量のボディを扱うインスタンス化サブシステム、そして最新の MSVC、Clang、PS5 の CPU に合わせたツールチェーンの作業です。
</def>
</deflist>

## シミュレーションの主要機能

### 剛体

- スタティック、ダイナミック、キネマティックのアクター
- ボックス、スフィア、カプセル、凸形状、三角形メッシュのコリジョンジオメトリ
- 摩擦、反発、密度を持つ物理マテリアル
- 重力、減衰、力、インパルス、トルク
- スリープ、ウェイク、アクティブなボディの追跡
- 高速に動くボディのための連続衝突検出
- コリジョンのフィルタリングと、シミュレーション用・クエリ用の形状フラグ
- 接触、オーバーラップ、ウェイク/スリープの通知

### シーンクエリ

PhysX はエンジン全体で使われるコリジョンクエリのパスを提供します。

- レイキャスト
- 形状のスイープ
- オーバーラップ
- 単一ヒットと複数ヒットのクエリ
- オブジェクトチャンネル、トレースチャンネル、プロファイルによるフィルタリング
- 移動、武器、ナビゲーション、ゲームプレイのシステムが使う同期的なシーンクエリ

クエリのコストは、コリジョンの複雑さ、ブロードフェーズに含まれる数、フィルターのコールバック、結果の数に依存します。繰り返し行うゲームプレイのクエリには単純なコリジョンを使い、最初のブロッキングヒットだけが必要な場合は複数ヒットの結果を要求しないでください。

### コンストレイント

統合は、Unreal のコンストレイントフレームワークを通じて、固定、距離、ヒンジ、球面、D6 形式のコンストレイントに対応しています。利用できる制御は次のとおりです。

- 直線と角度の制限
- モーターとドライブ
- 破断する力とトルク
- コンストレイントのプロジェクション
- コンストレイントで結ばれたボディ間のコリジョンの有効化
- 質量と慣性のスケーリング
- 物理アセットで作成するスケルタルのコンストレイントの連鎖

### キャラクターとスケルタルの物理

PhysX は、キャラクタームーブメントのコリジョンクエリと、物理アセットの剛体シミュレーションを提供します。これにはラグドール、フィジカルアニメーション、ヒットリアクション、ボディのウェルド、ボディごとのコリジョン設定が含まれます。

### ビークル

Vite は UE4.27 の PhysX のビークルスタックを維持しており、ホイールのシミュレーション、サスペンション、タイヤの摩擦、エンジン、ギア、デファレンシャル、ドライブトレインの設定を含みます。ビークルの挙動は、UE4 のプロジェクトで使われる標準のビークルとタイヤのデータアセットで作成します。

## 破壊、クロス、Blast

Vite の物理スタックには、次の NVIDIA のシステムが含まれます。

| 機能 | 役割 |
|---|---|
| APEX Destruction | 作成済みの破壊可能メッシュ、サポートチャンク、ダメージと破砕のイベント |
| APEX Cloth | 頂点ペイントによるクロスのコンストレイントと、スケルタルメッシュの衣服シミュレーション |
| NVIDIA Blast | PhysX バックエンドと統合された破壊アセットと破砕のワークフロー |

作成と実行時の指針は [破壊とクロス](Destruction-And-Cloth.md) を参照してください。

## Vite の拡張

### 最新ツールチェーンへの対応

Vite の PhysX 3.4 のライブラリとビルドファイルは、最新の MSVC と Clang（Android NDK の Clang を含む）に向けて近代化を進めるとともに、**PS5 の Zen 2 の削減された FPU**（`FP3` なし、`FP2` はストア専用、**256 ビットの FMA
パイプ 1 本**）に合わせて再調整しています。この作業はデスクトップの Matisse でも Series X でもなく、AMD 4700S で検証しています。Series X のトランジスタ数は 153 億、Oberon は 106 億で、その差の一部は CPU の FPU の回路です。そのため Series X は PS5 のコアにはできない FMA のデュアル発行ができます。カーネルのルール、計測方法、`V3ScaleAdd`
のパターンは [PS5 CPU の FPU](PS5-CPU-FPU.md) にまとめています。

### 固定タイムステップのシミュレーション

任意で使える固定タイムステップのパスは、シミュレーションの周期を可変のレンダーフレームから切り離し、レンダー補間を加えます。安定したシミュレーションのデルタや再現可能なキャプチャが必要なプロジェクト向けです。コンパイル時の設定と統合の要件は [固定タイムステップ](Fixed-Timestep.md) を参照してください。

### インスタンス化物理サブシステム

<img src="PhysXInstancedSubsystem.png" alt="PhysX のインスタンス化サブシステムでシミュレーションされた大量のインスタンス化剛体" border-effect="line"/>

*インスタンスごとに本物の PhysX のボディを持つインスタンス描画。[PhysX インスタンスサブシステムのデモ](PhysX-Instanced-Subsystem.md)
を参照してください。*

インスタンス化サブシステムは、ボディごとにアクターとコンポーネントの階層を持つ代わりに、インスタンスメッシュを使って大規模で均質な剛体の集合を表現します。破片、薬莢、環境オブジェクトなど、数の多いシミュレーション向けです。[インスタンス化物理](Instanced-Physics.md) を参照してください。

### ネイティブアクターのパス

<img src="NativePhysXActors1425.png" alt="1,425 個のキューブをシミュレーションする Vite のネイティブ PhysX アクターのエンジン内テスト。374 FPS" border-effect="line"/>

*ネイティブ PhysX アクターとしてシミュレーションする 1,425 個のキューブ: 374 FPS、フレームタイム 2.67 ms。4.27 のリリースではなく UE Vite 5.0 のビルドで記録したものです。[ベンチマークの注記](Physics.md#native-actors-1425) を参照してください。*

コンパクトなシミュレーション状態をすでに持っているエンジンレベルのシステムは、ネイティブの PhysX アクターに近い形で動作し、不要な上位のアクターやコンポーネントの処理を避けられます。これは特殊な統合パスであり、所有権、ライフタイム、トランスフォームの同期、コリジョンのフィルタリング、破棄は呼び出し側の責任です。

## 設定

物理の設定は **プロジェクト設定 > エンジン > 物理** にあります。

| 設定 | 役割 |
|---|---|
| Default Gravity Z | ワールドの重力。`-980.0` は 1 uu = 1 cm に相当 |
| Substepping | 長いフレームを小さなシミュレーションステップに分割 |
| Max Substep Delta Time | 1 回のサブステップで処理する最大のデルタ |
| Max Substeps | 1 フレームで実行するシミュレーションステップの上限 |
| Simulate Skeletal Mesh on Dedicated Server | サーバーのターゲットでスケルタルの剛体シミュレーションを有効化 |
| Default Degrees Of Freedom | 平面や軸が制限されたゲーム向けに動きを拘束 |

### サブステップ

サブステップを使わない場合、物理シーンはフレームのデルタで進みます。大きなデルタや変動するデルタは、接触とコンストレイントの安定性を下げることがあります。サブステップは必要に応じて複数の小さな前進を行い、その CPU コストは実行するサブステップの数に応じて増えます。

`Max Substep Delta Time` は安定を保つ必要がある最も速い相互作用から決め、次に `Max Substeps` で最悪時の処理量に上限を設けます。上限を設けることで、遅いフレームがシミュレーションの際限ない遅れを生むことを防げます。

フレームに応じたサブステップではなく、固定のシミュレーション周期を使う場合は、[固定タイムステップのパス](Fixed-Timestep.md) を使用してください。

## PhysX Visual Debugger

PhysX Visual Debugger は、接続したシーンのアクター、形状、接触、コンストレイント、シミュレーションの状態を調べられます。PVD 対応の開発ビルドを使い、問題を再現する前に接続し、ボディの多いシーンではキャプチャの時間を短く抑えてください。

PVD で完全なキャプチャを取る前に、作成したジオメトリとフィルタリングを確認するには、ビューポートのコリジョン表示が引き続き便利です。

## プロファイリング

| コマンド | 表示内容 |
|---|---|
| `stat physics` | エンジンのフェーズごとに分けた物理の時間 |
| `stat game` | ゲームスレッドの処理の中での物理のコスト |
| `show Collision` | ビューポートでのコリジョンジオメトリ |

代表的なコリジョンジオメトリ、ボディの数、スリープの挙動、イベントの生成でプロファイリングしてください。比較のたびに、物理のミリ秒、ボディ数と形状数、アクティブなボディの数、ソルバーの設定、サブステップ、ワーカーの構成を記録します。

ボディの数が多い場合は、同じ形状とソルバー設定で、標準のアクターベースのシミュレーションと
[インスタンス化サブシステム](Instanced-Physics.md) を比較してください。
