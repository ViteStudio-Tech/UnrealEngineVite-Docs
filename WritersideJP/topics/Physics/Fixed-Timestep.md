# 固定タイムステップ

<tldr>
<p>
フレームレートに依存しない固定のレートで PhysX を進め、レンダー補間で動きを滑らかに保つ、Vite の任意機能です。コンパイル時スイッチは <code>VITE_PHYSX_FIXED_TIMESTEP</code>（既定値 <code>0</code>）、実行時の CVar は
<code>p.VitePhysXFixedTimestep.Enabled</code> です。
</p>
</tldr>

既定では、Unreal はフレームのデルタタイムで物理を進めます。8&nbsp;ms かかったフレームでは物理を 8&nbsp;ms、33&nbsp;ms かかったフレームでは 33&nbsp;ms 進めます。そのためシミュレーションの結果はフレームレートに依存し、同じ入力でもハードウェアによって結果が変わり、あるマシンで記録したリプレイが別のマシンでは再現されません。

Vite の固定タイムステップモードは、この 2 つを切り離します。物理は常に同じ刻み幅で進み、コンポーネントは直近 2 つの物理状態の間に置かれるため、動きは滑らかに保たれます。

## 有効にする

これは 2 段階のオプトインです。既定ではこの機能はコンパイル対象から外れています。

<procedure title="固定タイムステップの物理を有効にする" id="enable-fixed-timestep">
    <step>
        <code>VITE_PHYSX_FIXED_TIMESTEP</code> を <code>1</code> に設定します。<code>CoreDefines.h</code> を編集せずに上書きする方法は <a href="Compile-Time-Switches.md">コンパイル時スイッチ</a> を参照してください。
    </step>
    <step>エンジンを再ビルドします。</step>
    <step>
        実行時に、または <code>DefaultEngine.ini</code> で <code>p.VitePhysXFixedTimestep.Enabled 1</code> を設定します。
    </step>
    <step>
        <b>プロジェクト設定 &gt; エンジン &gt; 物理</b> でサブステップを有効にします。固定ステップの実装はサブステップのパスを通って実行されます。
    </step>
</procedure>

コンパイル時のゲートがあるのは、この機能が物理シーン、サブステップのタスク、アニメーションの物理ブレンドのホットパスを変更するためです。決定論的な動作が不要なプロジェクトが、追加の分岐やダブルバッファのトランスフォームの保存領域のコストを支払うべきではありません。

## コンソール変数

以下はすべて、`VITE_PHYSX_FIXED_TIMESTEP` をコンパイルに含めた場合にのみ存在します。

| CVar | 既定値 | 範囲 | 用途 |
|---|---|---|---|
| `p.VitePhysXFixedTimestep.Enabled` | `0` | 0/1 | 全体の有効化 |
| `p.VitePhysXFixedTimestep.DeltaTime` | `0.01667`（1/60） | 0.0013〜1.0 | 固定のシミュレーションステップ（秒） |
| `p.VitePhysXFixedTimestep.MaxTimesteps` | `16` | 1〜50 | 過負荷が蓄積し始めるまでの、ゲームの 1 Tick あたりの固定ステップの最大数 |
| `p.VitePhysXFixedTimestep.MaxCumulativeExtraSteps` | `50` | 0〜100 | 制限ポリシーが適用されるまでの過負荷の累積予算 |
| `p.VitePhysXFixedTimestep.LimitType` | `0` | 0/1 | `0` は固定ステップを打ち切り、`1` は可変サブステップにフォールバック |
| `p.VitePhysXFixedTimestep.InterpolationMode` | `1` | 0/1/2 | `0` は無効、`1` はコンポーネント単位、`2` は常に補間 |

## 仕組み

実装は時間のバンクを保持します。ゲームの Tick ごとにフレームのデルタをバンクに加え、そこに収まるだけの固定ステップを丸ごと実行します。余りは次の Tick のためにバンクに残ります。

速いフレームでは固定ステップが 0 回、遅いフレームでは複数回になりうるため、標準のサブステップとは 3 つの点で扱いが異なります。

**物理ステップのないフレームではバッファを入れ替えません。** 標準のサブステップは、物理のターゲットバッファを Tick ごとに入れ替えます。固定ステップモードでは、ステップを実行するときだけ入れ替えます。そのため、ステップが 0 回のフレームでキューに入った一度きりの力、キネマティックの目標、独自の物理コールバックは捨てられず、次のステップを待ちます。

**独自の物理コールバックは一度だけキューに入ります。** バッファが複数のフレームにわたって残るようになったため、毎フレーム同じ独自の物理デリゲートを登録するコンポーネントでは、そのままだとコピーが積み重なってしまいます。固定ステップモードでは、各デリゲートをボディのキューに一度だけ追加します。

**結果の取得はステップが行われた場合のみです。** シミュレーションのないフレームでは `fetchResults` をスキップし、冗長な処理や古いトランスフォームの読み取りを避けます。

## 過負荷への対処

ヒッチが長い、または固定レートに対して物理の負荷が重すぎるなどでゲームが追いつけない場合、バンクは消化されるより速く増えていきます。放置すると悪循環に陥ります。各フレームが長くなり、より多くのステップがキューに入り、次のフレームがさらに長くなるのです。

`MaxTimesteps` は、過負荷として数えずに 1 Tick で実行できるステップ数です。それを超えたステップは 1 つごとに過負荷のカウンターを 1 増やし、それより少ないステップで済んだ Tick ではカウンターがその分だけ減ります。カウンターが `MaxCumulativeExtraSteps` 以内にある間は、バンクに収まるステップがすべて実行されます。ある Tick でこの予算を超えそうになると、`LimitType` が挙動を決め、ログに `Fixed Timestep limits exceeded` と出力されます。

| `LimitType` | 挙動 | 使う場面 |
|---|---|---|
| `0` &mdash; 打ち切り | 予算が許す分のステップだけを実行します（予算を使い切った後は最大 `MaxTimesteps`）。残りの時間はバンクに残り、以降の Tick で順に消化されます。 | すべてのステップを同じ大きさにしなければならない場合: リプレイ、決定論的なテスト |
| `1` &mdash; 可変サブステップ | バンクを空にし、この Tick を物理の設定の **Max Substep Delta Time** と **Max Substeps** を使った Unreal の通常の可変サブステップで進めます。カウンターが予算内に戻ると固定ステップに戻ります。 | 実時間に追従することが重要な場合: 一般的なゲームプレイ |

過負荷が続くと、打ち切りでは物理が実時間より遅れ、負荷が下がると 1 Tick あたり最大 `MaxTimesteps` ステップで追いつきます。どのステップも同じ大きさのままです。可変サブステップは物理を実時間に合わせ続けますが、フォールバックが働いた Tick では固定のステップ幅が崩れます。

## レンダー補間

120&nbsp;fps で描画しながら 60&nbsp;Hz で固定ステップを行うと、補間なしでは各物理状態が 2 回ずつ表示され、目に見えるカクつきが生じます。各ボディは直近 2 回のステップのトランスフォーム（`PreviousPhysicsTransform` と `LatestPhysicsTransform`）を保存します。物理の結果をコンポーネントに同期するとき、補間対象のコンポーネントは、バンクに残っているステップの端数に応じてその 2 つの間に置かれます。そのためコンポーネントはシミュレーションより最大 1 ステップ遅れます。`GetComponentLocation` はブレンドした位置を返し、ボディ自体は最新の物理状態のままです。位置は線形に、回転は球面線形に補間され、スケールは補間されません。テレポートやその他の明示的な `SetBodyTransform` の呼び出しでは保存した 2 つのトランスフォームがリセットされるため、テレポートしたボディが移動の間を引きずるように表示されることはありません。

`InterpolationMode` は、どのコンポーネントを補間するかを制御します。

- **`0` 無効。** ボディは最新の物理状態にスナップします。最も軽く、描画レートが固定ステップのレートと完全に一致する場合は正しい結果になります。
- **`1` コンポーネント単位（既定）。** `bInterpolateFixedTimestep` が設定されたコンポーネントだけを補間します。これは `UPrimitiveComponent` の C++ のメンバーで、既定ではオフで、ブループリントや詳細パネルには公開されていません。そのため既定のモードでは、コードで必要なコンポーネントに対してオンにするまで何も補間されません。
- **`2` 常に。** シミュレーションするすべてのボディを補間します。

スケルタルメッシュの物理ブレンドも同じ補間済みのトランスフォームを読むため、ラグドールや物理ブレンドしたアニメーションはスケルタルメッシュコンポーネントの設定に従います。

```cpp
// 固定ステップでもシミュレーションするメッシュを滑らかに動かしたいアクターのコンストラクターで
#if VITE_PHYSX_FIXED_TIMESTEP
    Mesh->bInterpolateFixedTimestep = true;
#endif
```

## ステップレートの選び方

`DeltaTime` は調整の中心となる判断です。

| ステップレート | 値 | 備考 |
|---|---|---|
| 30&nbsp;Hz | `0.03333` | 最も軽量。遅く重いオブジェクトなら許容範囲。速いボディはすり抜けます。 |
| 60&nbsp;Hz | `0.01667` | 既定値。一般的に良い選択です。 |
| 120&nbsp;Hz | `0.00833` | 高速な弾や硬いコンストレイントに向いています。CPU コストはおよそ 2 倍です。 |

物理のコストはステップレートに比例するため、120&nbsp;Hz のステップは 60&nbsp;Hz のおよそ 2 倍のコストがかかります。最も速く動くシミュレーション対象のボディが安定する最低のレートを選び、個別のすり抜けの問題はステップレートを上げるのではなく CCD で解決してください。

> ステップレートは早い段階で決め、コンテンツを調整した後は変更しないでください。インパルスの大きさ、コンストレイントの剛性、減衰の値といった物理のコンテンツは、暗黙のうちにステップレートに合わせて調整されています。後から変更すると、すべてを調整し直すことになります。
>
{style="warning"}

## 使うべき場面

**固定タイムステップを使うべき場面:** リプレイ、物理の結果を検証する自動テスト、クライアントとサーバーの結果を比較するネットワーク物理など、同じ入力から同じシミュレーションを得たいあらゆる場面。

固定ステップによってフレームレートの影響はなくなりますが、PhysX が結果を厳密に再現するのは、同じプラットフォームと同じビルドで同じ順序の API 呼び出しを行った場合だけです。**プロジェクト設定 &gt; エンジン &gt; 物理** の **Enable Enhanced Determinism** もオンにして、無関係なアクターの追加や削除で結果が変わらないようにしてください。また、異なる CPU やプラットフォームの間でビット単位で同一の結果になることは期待しないでください。

**使うべきでない場面:** 再現性の要件がないプロジェクト。既定の可変ステップのパスのほうが軽く、そのためにコンパイル時スイッチの既定値は無効になっています。
