# バックポート

<tldr>
<p>
Vite は UE 5.0 から UE 5.8 までのエンジンの成果を日常的にバックポートしています。LTS 以降の公開リリースの履歴には 100 を超えるバックポートのコミットがあり、その多くは複数の上流の変更をまとめたものです。このページでは、ライセンス、ABI、性能を壊さずにバックポートを行う方法を説明します。
</p>
</tldr>

Vite は、新しいエンジン向けに開発された技術に追従する NvRTX 4.27 Plus のフォークです。そのため、バックポートは例外ではなく日常的な作業です。

## これまでにバックポートしたもの

| 出所 | 例 |
|---|---|
| UE5 | 自明ではないレンダリングの最適化、広範な CPU の最適化、プラグイン、使い勝手の改善、アニメーションの機能、サードパーティのライブラリ |
| ベンダーの SDK | [DLSS 4.5、FSR 4、XeSS 3.1、Streamline](Upscalers.md)、TressFX 5.0、Blast |
| サードパーティのプラグイン | ACL、Motion Symphony、[Kawaii Physics](Bundled-Plugins.md) |

## バックポートの前に

<procedure title="バックポートの実現性の確認" id="backport-check">
    <step>
        <b>ライセンスを確認します。</b> UE5 のコードは Epic のライセンスの下にあり、Unreal Engine のフォークでの使用は認められますが、自由な再配布は認められません。サードパーティのコードは寛容なライセンス（MIT、Apache 2.0、BSD、Zlib）でなければなりません。<a href="Coding-Guidelines.md">コーディングガイドライン</a> と
        <a href="License-And-Copyright.md">ライセンスと著作権</a> を参照してください。
    </step>
    <step>
        <b>依存関係を確認します。</b> Nanite、Lumen、UE5 の RDG の API、Chaos の物理のインターフェイスに依存する UE5 の機能は、きれいにはバックポートできません。コードを書く前に、それが実際に何を必要とするかを把握してください。
    </step>
    <step>
        <b>ABI への影響を確認します。</b> その機能がシェーダーから見える構造体やパックされたビットマスクの変更を必要とするなら、そのままではバックポートできません。<a href="Coding-Guidelines.md">ABI のルール</a> を参照してください。
    </step>
    <step>
        <b>その価値があるかを確認します。</b> UE5 の問題を解決するために存在する UE5 の機能は、Vite では価値がないかもしれません。最適化、サードパーティのライブラリの更新、プラグインと SDK の更新、修正に注力してください。
    </step>
</procedure>

## よくある障害

<deflist>
<def title="RDG の API の違い">
UE5 の Render Dependency Graph の API は 4.27 から大きく変わっています。パスの宣言、リソースの遷移、ユニフォームバッファの作成のすべてが異なります。通常は機械的に置き換えられますが、レンダーパスのすべての行に手が入ります。
</def>
<def title="Chaos と PhysX">
UE5 で物理に触れるものはすべて Chaos を前提としています。Vite は PhysX です。<a href="PhysX.md">PhysX</a> を参照してください。物理に関わるバックポートでは、インターフェイスを置き換えるのではなく書き直す必要があります。
</def>
<def title="コアの型の変更">
UE5 はいくつかのコアの型を変更しており、最も目立つのは <code>FVector</code> の float から double の精度への移行です。バックポートでは全体にわたってその変更を元に戻し、精度が重要な役割を果たしていた箇所に注意する必要があります。
</def>
<def title="モジュールの再編">
UE5 はモジュールを分割し、名前を変えています。インクルード、ビルドの依存関係、モジュール名のすべてを、4.27 での場所に対応付け直す必要があります。
</def>
<def title="シェーディングモデルの枠">
シェーディングモデルは数の限られた列挙型です。Vite はすでに <a href="Shading-Models.md">Callisto BRDF、Toon、Lit Reactive</a> を追加しています。さらに追加すると枠を 1 つ使い、全体にシェーダーのパーミュテーションが増えます。
<a href="Shader-Compilation-And-PSO.md">シェーダーコンパイルと PSO</a> を参照してください。
</def>
</deflist>

## 作業を進める

### 変更を追跡できるようにする

将来の上流のマージの後でも識別できるように、[コーディングガイドライン](Coding-Guidelines.md) のインラインの変更の印をバックポートした領域に付け、コードの出所を記します。

```c++
//vite_begin_change - Backported from UE 5.3, CL 12345678
...
//vite_end_change
```

### コストのかかるものをガードする

その機能に、すべてのプロジェクトが望むわけではない実行時やコンパイル時のコストがあるなら、[コンパイル時スイッチ](Compile-Time-Switches.md) かコンソール変数の背後に置き、既定でオフにしてください。Vite の既存のスイッチはこのパターンに従っています。

| スイッチ | 既定値 | ガードするもの |
|---|---|---|
| `VITE_PHYSX_FIXED_TIMESTEP` | 0 | 固定タイムステップの物理 |
| `VITE_RT_PSO_DEBLOAT` | 1 | レイトレーシングのパーミュテーションの大部分をコンパイル対象から外す |
| `VITE_O_SSAO` | 1 | 最適化された SSAO の経路 |
| `VITE_DLSS_PATCH` | 0 | DLSS の半透明とボリュメトリックフォグの修正 |
| `VITE_NVRTX_TRANSLUCENCY_DEPTH` | 0 | NvRTX の半透明の深度の扱い |

`VITE_RT_PSO_DEBLOAT` は *制限的な* 値が既定であることに注意してください。機能のコストがシェーダーのパーミュテーションの数であるときは、ビルドを速く保つ既定値が優先され、その機能は任意で有効にするものとして文書化されます。

### 基準に対してテストする

バックポートした機能は、UE5 でどう動いていたかではなく、Vite の [パフォーマンス目標](Performance-Targets.md) に対して計測する必要があります。UE5 のフレームの予算に合わせて調整された機能は、Vite が対象とするハードウェアで動く 4.27 のプロジェクトでは手に負えないかもしれません。

## バックポートを文書化する

すべてのバックポートには次のものが必要です。

| 項目 | 場所 |
|---|---|
| 出典のリンク、上流のコミットやタグ | コミットの本文。[コミット規約](Commit-Conventions.md) を参照 |
| 置き換えの際に変更した点 | コミットの本文 |
| 新しいコンソール変数やスイッチ | ドキュメントのページ。該当する場合は [コンパイル時スイッチ](Compile-Time-Switches.md) にも |
| 利用可否の注意 | その機能のページに、目立つように |

最後の項目は見た目以上に重要です。既定でコンパイル対象から外れている、あるいはプラグインを有効にする必要があるバックポートした機能は、そうしなければ、使おうとした全員から壊れていると報告されます。

## アセットのバックポート

UE5 からの *アセット* のバックポートは別の問題で、コードではなく Asset Downgrader で扱います。[UE5 からの移行](Migrating-From-UE5.md) と [提案中のプラグイン](Proposed-Plugins.md) を参照してください。
