## フォークについて

### なぜ UE5 ではなく 4.27 なのか

多くの種類のプロジェクトにとって、UE5 の目玉機能は得られるもの以上のコストがかかるからです。Nanite、Lumen、Chaos は、活用するかどうかに関係なくそれぞれ基本コストを伴い、UE5 のコアクラスとティックのオーバーヘッドも大きくなっています。Vite は 4.27 の低い基準を出発点に、本当に価値のあったレンダリング技術を加えています。

数値を含む詳しい議論は [なぜ NvRTX 4.27 なのか](Why-NvRTX-427.md) と
[UE4 と UE5 のコスト分析](UE4-Versus-UE5-Cost-Analysis.md) にあります。

### Vite は標準の 4.27 をそのまま置き換えられるか

ほぼ置き換えられますが、完全ではありません。Vite は性能のためにエンジンの既定値をいくつか変更しています。オーバーラップイベントの扱い、スケルタルメッシュとアクターの既定値、シャドウのスケーラビリティ、ティックの挙動などです。標準の 4.27 から移行するプロジェクトはほとんどそのまま動きますが、何が変わったかを理解するために
[エンジンの既定値の変更](Engine-Defaults.md) を読んでください。移行中は `ViteDefaults.bat` でオーバーラップとスケルタルメッシュの既定値を元に戻せます。

### UE5 のマーケットプレイスのアセットを使えるか

そのままでは使えません。Asset Downgrader プラグインが UE5 のアセットを 4.27 に変換し、Nanite のジオメトリなど 4.27 に相当するもののないデータを取り除きます。4.27 に存在しない機能は移植できず、取り除かれるだけです。[UE5 からの移行](Migrating-From-UE5.md) を参照してください。

### Vite はどのプラットフォームに対応しているか

主に DirectX 12 の 64 ビット Windows です。Android と Linux（サーバー）にはツールチェーンとビルドの修正が入り、その他のプラットフォームは標準の 4.27 の対応を引き継ぎますが、テストも調整もされていません。コンソールの作業は非公開です。[対応プラットフォーム](Platforms.md) を参照してください。

### Vite を使うには Unreal Engine のライセンスが必要か

はい。Unreal Engine のソースビルドで使うものと同じライセンスです。Vite は 4.27 のフォークなので、ソースとエディタのツールは Epic の [Unreal Engine EULA](https://www.unrealengine.com/eula/unreal) の対象です。Vite で作ったプロジェクトはあなたのものです。[ライセンスと著作権](License-And-Copyright.md) を参照してください。

## セットアップとビルド

### どのツールチェーンが必要か

Vite は現在、Visual Studio 2026 と MSVC 14.51、Windows SDK 10.0.26100 で開発されています。`ViteSetup.bat` は、Visual Studio 2026 と MSVC 14.50 以上、または Visual Studio 2022 と MSVC 14.44 以上を、SDK 10.0.26100.7705 以上と組み合わせたものを受け付けます。両方の Visual Studio がインストールされている場合は、どちらを使うかを尋ねます。[ツールチェーン要件](Toolchain-Requirements.md) を参照してください。

### クローンしたばかりなのにビルドがすぐに失敗する

ほとんどの場合、.NET Framework 4.5 のリファレンスアセンブリが欠けています。最近の Visual Studio のインストーラーは既定でこれを含めなくなりました。[ビルドのトラブルシューティング](Build-Troubleshooting.md) を参照してください。

### ソースからビルドする必要があるか

エンジンの C++ を変更する場合や [コンパイル時スイッチ](Compile-Time-Switches.md) を変える場合だけです。それ以外は、[インストール済みビルド](Install-Binary-Build.md) のほうが早く動かせ、必要なディスクもはるかに少なくて済みます。

### ビルドにはどれくらい時間がかかるか

一般的なハードウェアでは、ソースビルドに数時間かかり、インストール済みビルドはそれ以上かかります。その後の初回起動ではシェーダーのコンパイルが大半を占めます。[シェーダーコンパイルと PSO](Shader-Compilation-And-PSO.md) を参照してください。

### エンジンがディスクを使いすぎる

[ViteSetup](ViteSetup.md) で Express の経路を選ぶか、`devops\` のデブロートのスイートを自分で実行してください。どちらもプラットフォームのバイナリ、テンプレート、サンプル、必要に応じてプラグインをツリーの外に移し、削除ではなくドライランでの確認と回復用のフォルダーを用意します。[デブロートガイド](Debloat-Guide.md) を参照してください。

## レンダリング

### レイトレーシングのコンソール変数を設定したのに何も起きない

これは最もよくある質問で、答えはほぼ必ず `VITE_RT_PSO_DEBLOAT` です。既定値は `1` で、次のもののシェーダーのパーミュテーションをコンパイル対象から外します。

- RTXDI（`r.RayTracing.SampledDirectLighting`）
- パストレーシング
- レイトレーシングの半透明と、両方のコースティクスのシステム
- ピクセルごとのレイトレーシングのグローバルイルミネーション
- ディファードではない反射の経路と、それに伴う反射内の半透明とレイトレーシングのリフレクションキャプチャ

コンソール変数は存在し、設定もできますが、何も描画されません。使うには `VITE_RT_PSO_DEBLOAT=0` でエンジンを再ビルドしてください。[コンパイル時スイッチ](Compile-Time-Switches.md) と [レイトレーシング](Ray-Tracing.md) を参照してください。

### そのまま使えるレイトレーシングの機能はどれか

動的 DDGI は既定で有効です。反射、シャドウ、アンビエントオクルージョン、スカイライトは既定のビルドに含まれ、コンソール変数で有効にできますが、最初は無効です。残りはコンパイル対象から外れています。一覧は
[レイトレーシング](Ray-Tracing.md) にあります。

### どの GI を使うべきか

ほとんどのプロジェクトでは DDGI と SSGI の組み合わせです。DDGI が低周波の間接光のバウンスを、SSGI がプローブのグリッドでは解像できない接触スケールのディテールを補います。何も動かないなら、静的 DDGI のほうが安価で正確です。ピクセルごとのレイトレーシング GI はリファレンス専用で、既定ではコンパイル対象外です。[グローバルイルミネーション](Global-Illumination.md) を参照してください。

### なぜ TAA ではなく SMAA なのか

TAA のゴースト、にじみ、動きの中でのぼやけは構造的なもので、調整の問題ではありません。SMAA は空間的な手法で、それらがありません。Vite の推奨手法で、`r.DefaultFeature.AntiAliasing=4` で選び、`r.SMAA.Quality` で品質を設定します。[アンチエイリアシング](Anti-Aliasing.md) を参照してください。

### どのアップスケーラーを使うべきか

NVIDIA のハードウェアで NVIDIA のユーザー向けに出荷するなら DLSS。ベンダーを問わない対応には FSR 4（DirectX 12、古い GPU
向けに FSR 3.1 の経路あり）か XeSS。時間方向の処理を持たない安価な代替には NIS。ほとんどのプロジェクトは複数を用意すべきです。[アップスケーラー](Upscalers.md) を参照してください。

### アップスケーリングを有効にするとボリュメトリックフォグがおかしい

それを直すのが `VITE_DLSS_PATCH` です。フォグを内部解像度ではなく出力解像度で描画する
`r.VolumetricFog.UseUpScaledSizeVolumetricFog` を、半透明の修正とともに追加します。既定値は `0` なので、再ビルドが必要です。[アップスケーラー](Upscalers.md) を参照してください。

### Vite に Nanite や Lumen はあるか

ありません。それらは UE5 の前提の上に作られた UE5 のシステムで、Vite が避けるために存在する基本コストを伴います。Vite が現在出荷している答えは、ジオメトリにはハードウェアテッセレーションと LOD、グローバルイルミネーションには DDGI と
SSGI です。Vite 独自の後継である、ジオメトリの **Vite Vertis** と、GI とリアルタイムのパストレーシングの **Vite ReSTIR**
は開発中です。[Vite Technology](https://vitestudio-tech.github.io/UnrealEngineVite-Docs/tech/jp/) のサイトを参照してください。

## 物理

### なぜ Chaos ではなく PhysX なのか

Vite が対象とする負荷では PhysX のほうが速く予測しやすく、UE5 で取り除かれた Apex Destruction と Apex Cloth も引き続き使えるからです。[PhysX](PhysX.md) を参照してください。

### 決定的な物理を得るには

`VITE_PHYSX_FIXED_TIMESTEP=1` で再ビルドしてから、`p.VitePhysXFixedTimestep.Enabled` を有効にします。コンパイル時のスイッチがなければ、コンソール変数は何もしません。[固定タイムステップ](Fixed-Timestep.md) を参照してください。

### 何千もの物理オブジェクトが必要

[PhysX Instanced Subsystem](Instanced-Physics.md) を使ってください。ボディごとにアクターを持つ従来の物理は、数千のボディでソルバーの限界ではなくアクターのオーバーヘッドに突き当たります。このサブシステムは、インスタンス化メッシュのトランスフォームを直接動かすことでそのオーバーヘッドを取り除きます。

## パフォーマンス

### Compiler Explorer で MSVC と Clang を比較計測できるか

できません。[Compiler Explorer](https://gcc.godbolt.org/) は各コンパイラが出力するアセンブリを表示するもので、生成されたコードの時間は計測しません。[Quick Bench](https://quick-bench.com/) は Linux 上の GCC か Clang を計測するもので、MSVC はありません。MSVC と clang-cl はローカルで計測してください。[Compiler Explorer](Compiler-Explorer.md) を参照してください。

### 最適化はどこから始めるべきか

`stat unit` で、Game、Draw、GPU のどれが最も大きいかを特定してください。間違ったものを最適化しても、フレームタイムはまったく改善しません。[プロファイリング](Profiling.md) を参照してください。

### ゲームスレッドがボトルネックになっている

よくある原因を、おおよそ頻度の高い順に挙げると、キャラクタームーブメントコンポーネント、アニメーションの評価、ブループリントのティックのロジック、そしてアクターのティック全般のオーバーヘッドです。[400 キャラクター CMC ベンチマーク](400-Characters-CMC-Bench.md) と [パフォーマンス目標](Performance-Targets.md) を参照してください。

### シェーダーのコンパイルに時間がかかりすぎる

避けられないと決めつける前に、実際のパーミュテーションの数を確認してください。使用中のシェーディングモデル、有効なプラグイン、品質レベルのすべてが掛け算で効きます。`VITE_RT_PSO_DEBLOAT=1` はすでにレイトレーシングのパーミュテーションの大部分を取り除いており、それが既定値である理由です。[シェーダーコンパイルと PSO](Shader-Compilation-And-PSO.md) を参照してください。

### 変更が反映されていないかのようにシェーダーが振る舞う

古いキャッシュです。まず `recompileshaders changed` か `recompileshaders global` を試してください。どちらも完全な消去よりはるかに安上がりです。それでも直らなければ `WipeShaderCache.bat` を実行してください。[キャッシュ管理](Cache-Management.md)
を参照してください。

## プラグイン

### エディタに機能が見当たらない

そのプラグインが有効になっているかを確認してください。同梱プラグインの多くは既定でオフです。既定で有効なのは RTXGI、ACL、カスタムのスプラッシュ画面だけです。プラグインのフォルダー自体がない場合は、ViteSetup の Express の経路が
`ViteDebloat_Moved` に移動した可能性があります。[同梱プラグイン](Bundled-Plugins.md) を参照してください。

### プラグイン X を同梱してもらえるか

4.21&ndash;4.27 と互換で、寛容なライセンスを持ち、サイズとコンパイルのコストに見合うなら、提案してください。UE5 専用のプラグインは対象外です。[提案中のプラグイン](Proposed-Plugins.md) を参照してください。

### デブロートのスクリプトが必要なプラグインを取り除いてしまった

`ExcludedPlugins.txt` は積極的で、多くのプロジェクトが使うプラグインも含まれています。移動モードで実行した場合、ファイルはエンジンのフォルダーの隣の `ViteDebloat_Moved` にあります。削除モードで実行した場合は失われているため、ソース管理から復元する必要があります。[デブロートガイド](Debloat-Guide.md) を参照してください。

## コントリビュート

### プルリクエストが最も早く却下される原因は何か

ABI の変更です。レイトレーシングのペイロードのビットフィールド、シェーダーから見える列挙型、パックされた RHI や
RenderCore のビットマスク、反射のビットマスクの定義、CPU と GPU で共有する構造体のレイアウトなどです。これらは、変更の他の部分に関係なく却下されます。[コーディングガイドライン](Coding-Guidelines.md) を参照してください。

### 再帰、仮想関数、テンプレートは使えるか

再帰は禁止です。新しい仮想関数には厳密な正当化が必要です。テンプレートは、コンパイル時間とバイナリサイズのコストに見合う場合を除いて推奨しません。ブループリントに公開する新しい関数には、明示的な承認が必要です。

### 変更はどうドキュメント化すればよいか

同じプルリクエストの中で行います。新しいコンソール変数は該当する機能のページに、新しい `VITE_*` スイッチは
[コンパイル時スイッチ](Compile-Time-Switches.md) に、変更した既定値は [エンジンの既定値の変更](Engine-Defaults.md) に記載します。[ドキュメントへの貢献](Documentation-Contributions.md) を参照してください。
