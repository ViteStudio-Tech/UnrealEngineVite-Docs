# なぜ NvRTX 4.27 なのか

<tldr>
<p>
Unreal Engine 4.27 は、<b>ライティング手法に依存しないレイトレーシングパイプライン</b> を持つ最後のバージョンで、設計としては他の AAA エンジンに近いものです。UE 5.1 以降、BLAS/TLAS の管理、カリング、レイヒット時のシェーディングは次第に Lumen、Nanite、VSM、GPU Scene と結合され、PhysX の API は削除されました。
</p>
</tldr>

長期にわたって維持するエンジンフォークにとって、ベースバージョンの選択は最も影響の大きい判断です。このページでは、Vite が UE5 のブランチではなく NvRTX 4.27 Caustics をベースにしている理由を説明します。

## レイトレーシングパイプラインの論点

Unreal Engine 4.27 のレイトレーシングパイプラインは、特定の手法に依存しません。アクセラレーション構造は特定のライティング手法に縛られない形で構築・更新されるため、サードパーティの GI や反射の手法を、レンダラーがすでに管理しているシーン表現に接続するだけで統合できます。

UE 5.1 以降、既定のレンダリングパス（レイトレーシングのシーン構築と更新を含む）は、Lumen、Nanite、仮想シャドウマップ、Temporal Super Resolution を中心に統合が進みました。具体的には次のとおりです。

- **BLAS/TLAS の管理** は、GPU Scene、Nanite のフォールバックメッシュ、ストリーミングされるレイトレーシング用ジオメトリに対応するよう変更されました。
- **カリング** も同じシステムを中心に作り直されました。
- **レイヒット時のシェーディング** は、ヒットした実際のサーフェスをシェーディングするのではなく、Lumen 独自の
  Surface Cache とメッシュカード表現への依存を強めました。

いずれも Lumen のためには妥当な判断です。しかし、これらが重なることで、別の RTGI や反射手法の統合は、シーンを利用する作業からシーンと戦う作業に変わります。DDGI が 4.27 にはきれいに統合でき、5.x では統合しにくい具体的な理由がここにあります。

並行して、PhysX が非推奨となり Chaos が優先されるにつれ、残っていた PhysX 固有の API と互換コードも段階的に削除されました。物理面の主張を PhysX に依存するフォークにとって、これだけでも UE5 のブランチは選択肢から外れます。

> 詳しい論拠と検証は、Vite のベースを UE4 の最新版に移行した際の技術リファレンス文書を参照してください。
> [4.27 と 5.0 の比較](https://docs.google.com/document/d/1gA0MGkzeWWzKkgwBDOP5xRPouSKaOIW6xlPZ2q6BXO0/edit?usp=sharing)
>

## NvRTX Caustics ブランチを選んだ理由

NvRTX 4.27 Caustics は、NVIDIA による Unreal Engine 4.27.1 のレイトレーシングブランチです。Epic の 4.27 に次のものを追加しています。

- DirectX 12 と DXR の改良、そして合成シーンではなく実際の Marketplace コンテンツで検証された、数々のレイトレーシングの性能最適化。
- DLSS、NVIDIA Reflex、改良されたデノイザー。
- レイトレーシングによるメッシュコースティクスとウォーターコースティクス。
- ラスタライズとレイトレーシングの半透明を共存させるハイブリッド半透明モードを含む、強化された半透明。
- 吸収と全反射に対応した、マルチバウンス屈折の最適化。
- 新しい SVGF ベースのデノイザー、エミッシブマテリアル対応、リザーバーリサンプリングによるファイナルギャザーを備えた ReSTIR GI。
- DDGI でライティングされたレイトレーシング反射を含む、エンジン側の DDGI の改良。

最後の項目は見た目以上に重要です。標準の 4.27 向けランチャー版 DDGI はあくまでプラグインですが、NvRTX の統合はレイトレーシングパイプラインの内部にまで及んでおり、それによってプローブを使ったレイトレーシング反射が可能になっています。[動的 DDGI](DDGI-Dynamic.md) を参照してください。

この作業がすでに済んだブランチから始めたことで、フォークは膨大な統合作業を省くことができ、レイトレーシング機能も
NVIDIA の出荷済みサンプルコンテンツで検証済みの状態から始められました。

## その上にマージしたもの

Vite はベースのまま固定されているわけではありません。次のものを完全にマージしています。

| 取り込み元 | 内容 |
|---|---|
| Epic UE 4.27 Plus | Epic による 4.27 への継続的な修正と更新、そして最後のツールチェーン準拠の更新 |
| NvRTX 5.0 | NVIDIA によるさらなるレンダリング作業をバックポート |
| AMD GPUOpen のエンジンブランチ | FSR と、コンソールの GPU に特に関係の深い AMD 固有のレンダリング最適化 |
| UE 5.0〜5.8 | リリースで 300 件以上、内部ステージングで 1,000 件以上のバックポート |

バックポートはやみくもにマージするものではありません。上流の変更は元の作者のままチェリーピックし、そのままでは適用できない場合は Vite のコードベースに合わせて適応させます（`[Adapted Backport]` のコミット）。作業するのは、Unreal Engine の非公開フォークを長年保守してきたエンジニアです。手順は [バックポート](Backporting.md) のページにまとめています。

## 反論とその答え

当然予想される反論は、「Unreal Engine 4 はもう終わったコードベースだ」というものです。実際にはそうではありません。UE4 で開発された最近および今後の AAA タイトルには、Stellar Blade（4.26、2024 年）、Days Gone Remastered
（4.11、2025 年）、Delta Force（4.22、2026 年）、Mortal Kombat 1（4.27、2023 年）、Mario &amp; Luigi: Brothership
（4.26、2024 年）、Princess Peach: Showtime!（4.26、2024 年）、Pikmin 4（4.26、2023 年）、そして Square Enix の
Final Fantasy VII Rebirth（4.26、2024 年）、Dragon Quest VII Reimagined（4.27、2026 年）、Final Fantasy VII:
Revelation（4.27、2027 年）があります。

いずれも PhysX を使って出荷されています。これらのチームは、特定の機能を維持し、品質とパフォーマンスの目標を達成するために UE4 にとどまりました。Vite が拠って立つ理由と同じです。UE4 は 4.27 Plus ブランチを通じて大手スタジオから更新を受け続けており、任天堂のプラットフォームでは今も優先的なターゲットです。

「非推奨のコードベースを使っている」ことと「フォークを保守している」ことの違いは、それを改良し続けている人がいるかどうかです。Vite の計画は、コアシステムの継続的な最適化、レンダリングコアの近代化、UI の改善、ツールチェーンの更新です。これまでの成果は [リリースノート](Release-Notes.md) を参照してください。
