# UE4 と UE5 のコスト分析

<tldr>
<p>
性能差の原因は 1 つのシステムではありません。シェーダーの命令数、物理、キャラクタームーブメント、メモリ、Slate、スケルタルメッシュ、Tick のコスト、レンダースレッドの構造、ブループリントのネイティブ化の廃止、そしてボリュメトリクスのシェーダーが、それぞれ独立して寄与しています。
</p>
</tldr>

このページでは、Unreal Engine 4.27 と最新の UE5 の間で測定されたコスト差がどこから生じるかをまとめます。「UE5 は遅い」というだけでは行動に移せません。*どの* サブシステムがどれだけ劣化したかを知って初めて、フォークを維持する価値があるかを判断できるからです。

裏付けとなる測定値は
[公開スプレッドシート](https://docs.google.com/spreadsheets/d/1TabQV7UTDLMHI9GVFCbMzXohax2Agm2qzET7tOOXN7w/edit?usp=sharing)
にまとめています。

## マテリアルとシェーダー

UE 5.1 からシェーダーモデル 6 が優先のレンダリングパスとなり、SM5 と SM6 の両方のパスでシェーダーの命令数が全般的に大きく増加しました。その後のバージョンでは、命令数とパーミュテーション数がさらに増えています。

Unreal Engine 4.27 は同じ見た目をより軽量なシェーダーで実現し、新機能を使うシーンに限らず、全体的に GPU 時間の短縮に直結します。

## 物理

Chaos は多くのワークロードで PhysX より大幅に遅く、その主な原因は SIMD の活用効率の低さ、比較的貧弱なマルチスレッド化、そして全般的に効率の劣る設計判断にあります。

社内のストレステストでは、物理がボトルネックとなるシナリオで Chaos は PhysX より 5 倍以上遅くなっています。この差は剛体シミュレーションに限らず、物理クエリ、コリジョン計算、トランスフォームの伝播にも及ぶため、物理シミュレーションをほとんど、あるいはまったく明示的に使わないプロジェクトでも、測定可能な CPU コストを支払うことになります。

<img src="ChaosVsPhysX3000.png" alt="3,000 個のキューブのシミュレーション。Unreal 5.7 の Chaos は 33.26 FPS、Vite の PhysX 3.4 は 157.88 FPS" border-effect="line"/>

*3,000 個のキューブのシミュレーション。Unreal 5.7 と Chaos（左）は 33.26 FPS（フレーム 30.07 ms）、Vite と
PhysX 3.4（右）は 157.88 FPS（フレーム 6.33 ms）で、実効フレームレートに 4.7 倍の差があります。*

実際的な影響は規模に表れます。同じ CPU 予算で、PhysX ならはるかに複雑なクロスシミュレーションや破壊を扱えます。[PhysX](PhysX.md) を参照してください。

## キャラクタームーブメントコンポーネント

CMC は世代を追うごとに重くなっています。Unreal Engine 5.6 と比べると、4.27 は移動とコリジョンの計算で 2.2〜2.8 倍高速で、この数字には PhysX のより速いスイープは含まれていません。

これは多数のプレイヤーや AI キャラクターが登場するシーンで支配的なコストとなり、実現できるシミュレーション規模を直接制限します。[400 キャラクター CMC ベンチマーク](400-Characters-CMC-Bench.md) のシーンは、まさにこれを測定するためのものです。

## メモリ

全体のメモリ使用量は、エンジンのバージョンが上がるたびに増えてきました。一般的なマルチプレイヤーマップのシーン（スタイライズドデモで測定）では、Vite は UE 5.7 より総メモリ使用量がおよそ 1 GB 少なくなっています。

携帯機、Switch 2、標準のコンソールなどメモリに制約のある環境では、1 GB は誤差ではありません。テクスチャプールが収まるか、スラッシングを起こすかの分かれ目になることがよくあります。

## Slate と UI

UE 5.0 から Slate の描画コストが大きく増え、Slate オブジェクトの更新、レイアウト計算、トランスフォームを扱う仕組みも複雑になりました。より高品質な UI 描画を追求した結果、UI の描画自体が重くなっています。

HUD、インベントリ、メニューを含めればほとんどのゲームが UI を多用するため、これは決してなくならない毎フレームのコストです。

## スケルタルメッシュ

スケルタルメッシュは 5.1 から 5.4 にかけて複雑になりました。4.27 のスケルタルメッシュコンポーネントの基本コストははるかに軽量です。

出荷されたゲームでは、スケルタルメッシュが CPU 負荷の最大の要因になることが多いため、これは不釣り合いなほど大きな影響を持ちます。さらに Vite は、最適化したスケルタルメッシュの設定を既定としています。[エンジン既定値の変更](Engine-Defaults.md) を参照してください。

## ワールドの Tick とゲームスレッド

新しい UE5 では Tick システム全般のコストが増え、物理、Niagara、コントローラーの Tick も重くなりました。これはゲームの内容に関係なく、毎フレームに一律にかかる負担です。

## レンダースレッド

Lumen、Nanite、VSM、仮想テクスチャ、TSR、Substrate、Chaos Cloth、Hair の統合が深まるにつれ、レンダースレッドは大きく断片化し、PSO も重くなりました。これらの機能が有効なときだけでなく、あらゆる状況でレンダラー全体の性能に影響します。

## ブループリントのネイティブ化の廃止

見落とされがちですが、実際のプロジェクトでは最大の要因になることが多い項目です。

ブループリント VM は低速なランタイムです。単純なゲームプレイロジックでは、同等のネイティブ C++ より一般に
50〜80 倍遅く、ソート、ノード操作、経路探索などのアルゴリズム的な処理では 150〜400 倍遅くなることがあります。

Unreal Engine 4 では、ブループリントのネイティブ化がパッケージング時にブループリントのバイトコードをネイティブ C++ に変換することでこれを緩和し、VM 実行よりおよそ 10 倍速いコードを生成していました。UE5 はこの機能を削除しました。

ほとんどの Unreal プロジェクトはブループリントに大きく依存しており、特に自分では管理できないプラグインやサードパーティ製のコードを通じてその傾向が強いため、ネイティブ化を維持することで実際のプロジェクトにおける UE4 のゲームスレッドは大幅に高速になり、入力遅延の削減、応答性の向上、より大きなシミュレーション規模につながります。

## ボリュメトリクス、フォグ、エンジンのシェーダー

ボリュメトリクス、フォグ、スカイを扱うシステムとマテリアル、そして多くの既定のエンジンシェーダーで、大きな性能の劣化があります。シェーダーの複雑化は、前述のマテリアルの基本コストの増加にさらに上乗せされます。

劣化は既定のエンジンシェーダーそのものにあるため、プロジェクトが独自のボリュメトリックマテリアルを作るかどうかに関係なく影響します。

## コアクラスの基本コスト

個々のシステムとは別に、ゲームロジックとレンダーロジックの両方で、コアとなるエンジンクラスの基本コストが増えています。最も明確に測定できるのはインスタンスあたりのメモリで、同じコアクラスの `sizeof` が 4.27 から UE5 にかけて大きく増えています。

| クラス | 4.27（バイト） | 5.6（バイト） | 5.7（バイト） | 最新版と 4.27 の差 |
|---|---:|---:|---:|---:|
| `UObject` | 48 | 48 | 48 | +0% |
| `UActorComponent` | 184 | 232 | 232 | **+26%** |
| `AActor` | 752 | 1,096 | 1,128 | **+50%** |
| `AStaticMeshActor` | 768 | 1,112 | 1,144 | **+49%** |
| `ASkeletalMeshActor` | 888 | 1,224 | 1,256 | **+41%** |
| `UStaticMesh` | 992 | 1,984 | 2,008 | **+102%** |
| `USkeletalMesh` | 1,660 | 2,296 | 2,328 | **+40%** |
| `UAnimInstance` | 768 | 1,120 | 1,136 | **+48%** |
| `UAnimBlueprint` | 1,448 | 1,712 | 1,712 | **+18%** |
| `UAnimMontage` | 728 | 880 | 880 | **+21%** |
| `FRenderResource` | 16 | 40 | &mdash; | **+150%**（5.6） |
| `FStaticMeshVertexBuffer` | 136 | 208 | &mdash; | **+53%**（5.6） |

これはゲームのコードが動き出す前から支払うコストです。そのため、新しい機能を何も使わないプロジェクトにも現れます。レベル内のすべてのアクター、すべてのコンポーネント、読み込まれたすべてのメッシュが大きなフットプリントを抱え、オブジェクトが大きいほど、エンジンが反復処理する間に CPU キャッシュに残れる数は少なくなります。`UObject` 自体は変わっていないため、増加はその上に構築されたエンジンクラスで起きています。
